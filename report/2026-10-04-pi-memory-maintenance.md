# pi 记忆维护报告（2026-10-04）

首轮维护。范围是 `quanttide-founder` 一个项目的项目记忆，外带全局三份真源（`MEMORY.md`、`USER.md`、`failures.md`）。

## 发现了什么问题、原因是什么

**索引比真源多 39 条。** 逐条比对 sqlite 的 `memories` 表与 Markdown 真源：251 对 212，差额散在 7 个项目上，最大一块是 26 条**没有项目归属**的孤儿——真源里一条都没有。原因是条目被删除或合并之后索引没有同步清理。手册规定「冲突时以事实源为准」，代价是索引能长期偏多。

**项目记忆按 cwd 目录名切分，子目录里的活记到父项目头上。** `qtfounder` 是 `quanttide-founder` 下的子模块，它的项目记忆是**空的**：`project='qtfounder'` 的会话 0 个，在 `apps/qtfounder` 目录下跑过的会话 0 个。原因是它的活全部在上级目录里干的，上下文因此落进了 `quanttide-founder` 的项目记忆。

**工作记忆里混着大量状态快照。** 252 条全扫，49 条含版本号、当前数值或目录清单（「当前 56」「判 6/7」「[1.1.0]」这类）。手册写明「状态快照写入即腐烂，事实归仓库」，这些内容却还在池里当记忆用。

**内容过时了没人发现。** 有一条说创作谈、日志、设定迁至 `assets/memory` 的 `write/`，实际那里没有 `write/`，真身在 `examples/quanttide-founder-lab/data/write/`。这正是手册预言的：记忆中的副本无人维护，必然落后于正本。

**授权躺在池里当便条。** `STANDING.md` **根本不存在**，而「用户互动红线」「工作纪律」这类不可协商的条目都躺在 `MEMORY.md` 与 `failures.md` 里。手册写着「记忆靠 agent 主动搜索，规定等不到那一刻」——授权放在需要时才会被搜到的位置，等于没有。

**脱敏口径一度过严。** 首轮按 gallery 那份「六类不入库」执行，把作品名、发布平台、仓库内部路径、提交号一并抹掉；但来源仓本就是公开仓库，这些内容都可公开。口径因此改为只藏本机敏感与部署敏感两类。

**归档被当成了正本。** 首轮归档把 13 条原样搬进 `data/context/profile/quanttide-founder/`，其中「正本在别处」的部分在 quanttide-founder 的子仓里已有一份，形成两份正本。后来以「两条独立路径」的规则澄清：仓库自身的长期记忆服务仓库本身，本仓的归档服务 pi 第二大脑建设，两者不互为副本。

**维护动作本身出过三处工程差错，都在推送上。** 一是子模块推送被拒后没有停下，继续把父指针推了出去，产生悬空指针；二是 `git add` 的工作目录算错，改动没有暂存，但 commit 照样生成、push 照样成功，推上去的是「只删未补」的中间态；三是当时只核对了「本地 == 远端」的 hash——hash 相等只证明推成功，不证明推对了内容。

## 如何解决

**备份先行。** 动手前把 3 份全局真源与 31 份项目级真源复制到本机备份目录，逐字节校验一致，可随时回滚。

**把检查做成可重跑的脚本。** 本机脚本 `pi-memory-scan.py`：扫本机敏感（本机路径、密钥形态）与部署敏感（域名、对象存储桶、CDN），另扫状态快照（版本号、当前数值、目录清单）；有命中时退出码非零，可直接接进 CI 或 pre-commit。首轮实测 252 条中需处理 62 条，其中真密钥 0 条。

**授权层落地。** 新建 `STANDING.md`，18 条 / 846 字符，按 memory-pin 规范写：带边界、无论证、绝对措辞。授权条目随即从池中移出。

**工作记忆按「一个正本一条指针」收敛。** `quanttide-founder` 从 13 条 / 8969 字节压到 7 条 / 2072 字节（-77%）：正本在仓库的改成指针（3 条），状态快照删掉（3 条），无仓库正本的创作意图与工具经验留池（4 条）。

**先搬后删。** 只有内容确实进了仓库才从池里删。DAG 渲染那两条本想删，查证发现 `apps/qtgame-war` 的文档里根本没有这段设计，于是改标「待搬」，不删。

**推送纪律补两条。** 每条 git 命令带显式工作目录；push 之后除了核对 hash，还要把远端文件读回来核对内容；子模块推送失败立即停。
